# Design Document: CoderBot - Autonomous Coding Agent

## 1. Overview

CoderBot is an autonomous agent designed to implement coding tasks within the Ajapopaja pipeline. It takes a design document as input, clones the project repository into a sandbox, creates a feature branch, and uses a suite of coding and verification tools to fulfill the task. Upon completion, it submits its work for review via a Pull Request mechanism integrated into the Ajapopaja system.

## 2. Goals & Non-Goals

### Goals
- Automate the implementation of tasks described in design documents.
- Provide a safe sandbox for code modifications.
- Integrate with existing git workflows (cloning, branching, committing).
- Provide tools for file manipulation, linting, and testing.
- Facilitate human review via a UI for pull requests.

### Non-Goals
- Full-scale project management.
- Complex git operations like merging or rebasing (initially).
- Handling pull requests after they are created (managed by separate logic/UI).

## 3. Architecture

CoderBot follows the standard Ajapopaja bot architecture:

- **`CoderBotSession`**: Inherits from `BaseBotSession`. Manages the conversation loop and tool execution.
- **`CoderBotManager`**: Orchestrates session creation and lifecycle.
- **`CoderBotRegistry`**: Holds the tool definitions.
- **`PullRequest` Model**: A new MongoDB document to track bot-generated work.

### 3.1. Sandbox Environment

CoderBot will operate in a temporary directory.
- Root: `/tmp/ajapopaja/coderbot/<task_id>/`
- Action: `git clone <workspace_root> .`
- Action: `git checkout -b coderbot/<task_id>`

### 3.2. Tools

#### Read-Only Tools (Reused)
- `tree`, `read_source_file`, `grep`, `find`.
- `git_status`, `git_diff`, `git_log`.

#### Coding Tools
- `write_file(path, content)`: Overwrites or creates a file.
- `write_file_partially(path, old_string, new_string)`: Surgical edits (similar to `replace`).

#### Verification Tools
- `lint()`: Runs project-specific linting (e.g., `ruff`, `eslint`).
- `test()`: Runs project-specific tests (e.g., `pytest`, `npm test`).

#### Termination Tool
- `task_completed(summary)`: Marks the task as done and triggers the PR creation.

## 4. Design Decisions & Challenges

### 4.1. Sandbox Isolation
**Challenge**: Ensuring the bot's changes don't affect the main workspace until approved.
**Decision**: Use a separate directory for cloning. The clone will be a local clone from the `pipeline.workspace_path`.

### 4.2. Tool Parameter Validation
**Challenge**: LLMs might provide incorrect paths or malformed strings.
**Decision**: Strict validation in tool functions. Paths must be relative to the sandbox root and cannot escape it. We use a `safe_join` utility that resolves paths and verifies they remain within the assigned sandbox directory, explicitly rejecting directory traversal (`..`) and absolute paths.

### 4.3. Pull Request Creation
**Challenge**: How to bridge the gap between the sandbox branch and the main repo?
**Decision**: Since we are using local clones, the "Pull Request" in Ajapopaja will store:
- `branch_name`
- `patch_file` (generated by `git diff main...branch`)
- `summary`
- `task_id` and `pipeline_id`

### 4.4. Verification Logic
**Challenge**: Different projects have different lint/test commands.
**Decision**: Initially, we might need a way to detect or configure these commands per pipeline. For the MVP, we can assume standard commands for the current project or pass them in the system instruction.

## 5. Implementation Plan

### Step 1: Basic Scaffolding
- Create `backend/api/src/api/coderbot/` structure.
- Implement `CoderBotSession` with a minimal `get_system_instruction` and `task_completed` terminal tool.
- Add `PullRequest` model to `core`.

### Step 2: Infrastructure & Tools
- Create helper classes for Git operations (clone, branch, diff, cleanup).
- Implement `write_file`, `write_file_partially`, `lint`, and `test` tools.
- Add thorough unit and integration tests for these tools, ensuring proper cleanup of the sandbox.

### Step 3: Intelligence & Wiring
- Write the full system instruction for CoderBot, emphasizing precision, testing, and idiomatic code.
- Wire the session to use the git helpers during initialization.
- Ensure `task_completed` triggers the PR document creation in MongoDB.

### Step 4: UI Integration
- Update `PipelineDetailView` to show a list of open Pull Requests.
- Implement a simple "View PR" and "Accept/Reject" UI (FIFO sorted).
- Integrate `CoderBotClient` in the frontend.

## 6. Data Models

### 6.1. PullRequest (MongoDB)
```python
class PullRequest(Document):
    pipeline_id: str
    task_id: str
    summary: str
    branch_name: str
    patch: str  # The git diff output
    status: str # "open", "accepted", "rejected"
    created_at: datetime
    updated_at: datetime
```

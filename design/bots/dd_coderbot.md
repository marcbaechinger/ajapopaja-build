# Design Document: CoderBot – Autonomous Coding Agent

## 1. Overview

CoderBot is an autonomous agent that implements coding tasks described in design documents. It operates inside a sandbox, clones the project repository, creates a feature branch, and uses the **Pi** coding agent in headless RPC mode to generate and execute code. When finished, it submits a pull request for human review.

## 2. Goals & Non‑Goals

### Goals
- Automate the implementation of tasks described in design documents.
- Provide a safe sandbox for code modifications.
- Integrate with existing git workflows (cloning, branching, committing).
- Use the Pi coding agent for all code generation and tool execution.
- Facilitate human review via a UI for pull requests.

### Non‑Goals
- Full‑scale project management.
- Complex git operations such as merging or rebasing (initially).
- Handling pull requests after creation (managed by separate logic/UI).

## 3. Architecture

CoderBot no longer relies on the old `BaseBotSession` or the local Ollama LLM. Instead it orchestrates a subprocess that runs `pi` in **RPC** mode.

- **CoderBotSession** – Manages the lifecycle of a task, creates the sandbox, spawns the Pi subprocess, and streams Pi events to the frontend.
- **CoderBotManager** – Queues and serialises `CoderBotSession` instances.
- **PullRequest** – MongoDB document that records the PR generated by CoderBot.
- **Pi RPC** – A headless JSON‑over‑stdin/stdout protocol defined in the Pi documentation. CoderBot sends a `prompt` command with the task description and streams `message_update` events back to the UI.

### 3.1. Sandbox Environment

- Root: `/tmp/ajapopaja/coderbot/<task_id>/`
- Clone the workspace repository: `git clone <workspace_root> .`
- Create a feature branch: `git checkout -b coderbot/<task_id>`

### 3.2. Communication with Pi

| Phase | Pi Command | Description |
|-------|------------|-------------|
| Start | `pi --mode rpc --no-session` | Launch Pi as a subprocess in RPC mode. |
| Prompt | `{"id":"req-1","type":"prompt","message":<task>}` | Sends the combined design document and spec. |
| Events | JSON lines on stdout | `message_update`, `agent_end`, `tool_execution_*`, etc. |

The CoderBot session forwards `message_update` events (especially `text_delta` and `thinking_delta`) to the frontend as `ASSISTANT_STREAM` WebSocket messages. When an `agent_end` event is received, the session commits changes, generates a patch, creates a `PullRequest`, and notifies the UI with `PULL_REQUEST_CREATED`.

### 3.3. Tool Execution

All tooling (file editing, linting, testing) is performed by Pi. CoderBot does **not** expose its own tool registry; it simply forwards Pi’s events to the frontend. The Pi process uses its built‑in tools such as `write_file`, `write_file_partially`, `lint`, `test`, and `task_completed`.

### 3.4. Front‑end Streaming

The CoderBot session streams Pi events to the frontend in real time. Events of type `message_update` are mapped to WebSocket `ASSISTANT_STREAM` messages, ensuring the user sees incremental progress.

### 3.5. Structured Session Logging

CoderBot sessions persist all Pi interactions to a task‑specific JSON Lines file. Logs are written under the sandbox’s `logs` folder:

```
<SANDBOX_ROOT>/logs/<task_id>/coderbot_YYYYMMDD_HHMMSS.jsonl
```

Each line records an event with an ISO‑8601 timestamp. Supported event types:

| Type | Payload | Description |
|------|---------|-------------|
| `session_start` | `pipeline_id`, `task_id` | Session initialized |
| `pi_rpc_event` | `event` (raw Pi JSON) | Raw event from Pi stdout |
| `session_end` | `success`, `error` (optional) | Session completed |
| `error` | `message` | Any error encountered during the session |

Logging is controlled by `config.BASEBOT_LOG_ENABLED`. When enabled, the session ensures the directory exists before appending, providing auditability and easy replay for debugging.

## 4. Design Decisions & Challenges

### 4.1. Decoupling from BaseBotSession
**Challenge**: Remove tight coupling with the old bot infrastructure and Ollama.
**Decision**: Replace inheritance with composition; CoderBotSession is a plain async class that orchestrates Pi via a subprocess.

### 4.2. Using Pi RPC
**Challenge**: Guarantee deterministic communication and correct event ordering.
**Decision**: Use strict JSON‑L (one JSON object per line) protocol and an async subprocess loop to read and write.

### 4.3. Sandboxing & Git
**Challenge**: Ensure modifications are isolated until the PR is created.
**Decision**: Create a per‑task temporary clone, work on a feature branch, and commit only after Pi finishes.

### 4.4. Front‑end Streaming
**Challenge**: Present real‑time assistant output to the user.
**Decision**: Map Pi’s `text_delta` and `thinking_delta` to WebSocket `ASSISTANT_STREAM` messages.

## 5. Implementation Plan

1. **Refactor CoderBotSession** – Remove `BaseBotSession` inheritance; add async Pi subprocess handling.
2. **Update CoderBotManager** – Queue sessions and run them sequentially.
3. **Update UI** – Consume `ASSISTANT_STREAM` and `PULL_REQUEST_CREATED` events.
4. **Remove legacy tools** – Delete `tools.py` and the tool registry.
5. **Add tests** – Mock Pi subprocess and verify event handling.
